# Taxonomy of generated test cases — format, type, selection

**Jira:** KING-22942 · **Related:** KING-22737 (QA plugin), KING-22797 (scope marker),
KING-22213 / KING-22214 (smoke skills), KING-22420 (smoke promotion)
**Author:** Dmytro Kapeliukh · **Date:** 2026-09-24 · **Status:** Design. §5 decided, critic review folded in (2026-09-24), §6 decided

---

## 1. Problem

The plugin is about to generate cases in bulk, and three separate questions are currently
answered by one field:

- **Format**: how a case is written.
- **Type**: what the case is for.
- **Selection**: when the case runs.

`type: e2e` describes how a case is written, not what it is for. "Smoke" is claimed by two
things: the Story smoke test that `smoke-plan` produces in kinoa-test-automation, and a
possible case type in this plugin. This spec records one meaning for each axis. It also covers
moving the smoke skills into this plugin, which is what makes "smoke" have a single owner.

**Fact checked on 2026-09-24:** project KINOA holds **zero** cases tagged `qa-generated`.
Nothing the plugin authored needs migrating, so every rename below is free.

## 2. Decisions

### 2.1 Format: exactly two, `smoke` and `e2e`

The plan-level marker from KING-22797 **is** the format. Its values become
`scope: smoke | e2e`. The value `story` is retired, and there is no third format.

| | Smoke | E2E |
|---|---|---|
| Question it answers | Is the main feature live and working? | Is the Story fully covered? |
| Cases per plan | **One** scenario | As many as the ACs need |
| Steps | About 2–5. This is **guidance, not a gate**: 3, 6 or 7 are fine | No limit: a long journey or a short focused check |
| `type` | Always `functional` | Any of the five types (§2.2) |
| `→ expected:` per step | Exactly one | One or more |
| ACs per case | One or more | One or more |
| AC coverage | Advisory: uncovered ACs are reported, not failed | Every AC covered (as today) |
| Source of truth | The Jira "Smoke test" sub-task | `test-plan.md`, then Allure TestOps |
| TestOps | Only on request (§2.4) | Always, after the Step D gate |
| TestOps status and Feature | `Draft`, the caller's Feature | `Review`, the caller's Feature (§5.1) |
| Generated by | `/kinoa-qa:smoke-plan` | `/kinoa-qa:testplan` |

§4 lists which of these rules the validator enforces and which are guidance only.

**E2E is the full-coverage plan.** Everything `testplan` generates under today's default
`story` scope (per-AC functional, negative, edge, regression, nonfunctional cases) is generated
under `e2e`. A journey that covers several ACs, with several expected results on a step, is
allowed but not required. No step count and no AC count is enforced.

**Smoke is one short functional scenario.** It stops at "the feature works". Detail checks
(exact labels, filtering rules, status values) belong to the e2e plan, or become open
questions on the sub-task.

### 2.2 Type: five values, and `e2e` leaves the list

`type:` ∈ `functional | negative | edge | regression | nonfunctional`.

- `e2e` is removed. It is a format, and the format already lives in the header.
- `type` is **still not pushed to TestOps** (no `type-*` tags, unchanged). Its only job is to
  drive the QA-lens generation rules in `generation.md`, and those rules apply to e2e plans.
  A smoke case is always `functional`.
- QA-lens rule 4 ("End-to-end: only when the SoT describes a cross-component flow") is
  replaced. Whether journeys are written is now a property of the plan's format, not of a
  case type.

### 2.3 Selection: no separate axis

A case is in the fast lane because it is the smoke scenario. There is no `smoke` tag, no
selection field and no marking of existing cases.

### 2.4 Smoke plans: Jira is the source of truth, TestOps on request

`smoke-plan` and `smoke-run` keep their workflow: read the sources, draft, confirm, create the
"Smoke test" sub-task, run it, report on it. Neither creates a TestOps **test case** by default.
The move (§2.5) makes these edits to that workflow, and no others:

- `smoke-plan`: "Typically 5–12 numbered steps" (`smoke-plan/SKILL.md:155`) becomes "about
  2–5, not a limit". Its own opt-in "create a TestOps case" path (`:42`, `:385-390`) is
  removed and points at the push below. The "lives in kinoa-test-automation" rationale
  (`:33-34`) is rewritten.
- `smoke-run`: it keeps publishing a TestOps **launch** against a case id when one exists
  (`smoke-run/SKILL.md:192`, `:430-434`). A launch is a run result, not a case. It reads that
  id from the remote link the push writes (below).

The invariant is: **`testplan` is the only code that creates or updates TestOps test cases.**
Launches stay with `smoke-run` and KING-22420.

**Push to TestOps (opt-in).** On request, a **deterministic converter**,
`skills/testplan/scripts/smoke_to_plan.py` (with a `__main__` entry point and unit tests),
turns the sub-task into `<STORY-KEY>-smoke.test-plan.md`. That plan then goes through
`testplan`'s existing path: validator → Step D human gate → Step E upsert. No LLM step writes
the plan.

The converter either produces a plan that passes every validator check, or refuses and names
why:

| Plan element | Comes from |
|---|---|
| `story:` / `title:` header, `issues`, `Suite` | The **parent Story**, never the sub-task |
| `target:` header | The same service/capability resolution `testplan` Step A uses for that Story |
| `scope:` | `smoke` |
| `## Acceptance Criteria` | The parent Story's ACs, numbered by the same rule as Step A, so `[AC-n]` on the sub-task and `AC-n` in the plan name the same criterion |
| `## Conflicts` | The header, empty |
| `## Gaps` | One line per open question on the sub-task |
| One case, `type: functional`, `priority: P1` | Fixed |
| `purpose:` | `Verify that <sub-task summary without the "Smoke test: " prefix>.` |
| `source:` | `ac: AC-n, AC-m, …` from the per-step `[AC-n]` tags, in citation order, no duplicates. No `[AC-n]` anywhere → `QA-added: smoke scenario with no AC citation` |
| `preconditions:` | The sub-task's Preconditions block, one statement per line |
| `steps:` | The numbered steps, parsed from `smoke-plan`'s own step grammar (`**1. [GATE]**` + `*Expected:*`, sub-steps such as `**2a.**`), each rewritten as `n. <action>` + one `→ expected:` |
| Step text | All tags removed: `[AC-n]`, `[Story]`, `[PRD: …]`, `[Figma: …]`, `[live-confirmed]`, `[Figma → live-confirmed]`, `[PRD → live-confirmed]`, `[GATE]`. The Grounding line and FE `data-testid` requests are dropped |
| `expected:` | The expected results of the `[GATE]` steps, joined. No `[GATE]` step → refuse (the plan is not runnable either, per `smoke-run`) |

The converter **refuses** a sub-task with a step that has no expected result, such as a step
blocked by an open question: resolve the question first. Tag parsing is tested with a value
that contains `]` and `,`, because a value may legitimately contain the delimiter (CLAUDE.md).

**Case id write-back.** After Step E, the assigned id is written onto the sub-task as a
**remote link** titled `Allure TestOps case <id>`, pointing at the case. It is never written
into the description, which is the plan. `smoke-run` reads the id from that link. This is the
first Jira write `testplan` makes, so it gets its own confirmation at the Step D gate and needs
the `write:jira-work` scope, which the README says is unused today (§6.1).

The pushed case goes to TestOps as `Draft`, with the caller's `Feature`. It reconciles only
against the smoke plan's own case set (same `target:` marker plus `scope: smoke`), so a smoke
push never touches the Story's e2e cases. The plan file is rebuilt from the sub-task on every
push and is never hand-edited. Promotion to a Playwright regression test (`@allure.id`) stays
with KING-22420 and `testops-to-playwright`.

### 2.5 The smoke skills move into this plugin

| From kinoa-test-automation | To kinoa-qa |
|---|---|
| `.claude/skills/smoke-plan/SKILL.md` | `skills/smoke-plan/SKILL.md` |
| `.claude/skills/smoke-run/SKILL.md` | `skills/smoke-run/SKILL.md` |
| `.claude/skills/shared/step-outcome-contract.md` | `skills/shared/step-outcome-contract.md`. `testops-manual-run` stays behind and still uses it (§6.2) |
| `scripts/jiraReport.mjs`, `scripts/jiraAttach.mjs` | `skills/smoke-run/scripts/` |

- **Two separate skills**, `/kinoa-qa:smoke-plan` and `/kinoa-qa:smoke-run`, not merged into
  `testplan`. After reading the sources, the smoke flow (Jira sub-task) and the e2e flow
  (`test-plan.md` → TestOps) share almost nothing.
- **This is a move, not a redesign.** Only the edits in §2.4 and the path and prerequisite
  changes below are made. Two things are **separate tickets** (§6.3):
  - extracting a shared source-reading reference for `testplan` and `smoke-plan`;
  - the three improvements from the KING-22213 comment of 2026-09-21: sub-task comments as a
    named source, a tag for them, and an "AC with no implementing sub-task" readiness signal.
- **The scripts stay in Node.** They import only `node:fs` and `node:path` and read `JIRA_*`
  environment variables. They are called by a path relative to the plugin's skill directory,
  not `node scripts/jiraReport.mjs` from the repo root (`smoke-run/SKILL.md:288`).

**What `smoke-run` needs that the plugin does not provide.** The plugin owns no MCP
configuration (`README.md:101-102`). So each of these becomes a prerequisite the skill checks at
the start, stating plainly what is missing:

| Dependency | Today | After the move |
|---|---|---|
| Playwright MCP | Declared in kinoa-test-automation's `.mcp.json` | A documented prerequisite. `smoke-run` detects it with `ToolSearch` and stops if absent |
| `JIRA_*` environment variables | Read by the scripts | Documented in the plugin README, checked before the first script call |
| Data setup via `api/controller/` | Repo code | Only inside kinoa-test-automation. Elsewhere: setup through the UI, and the report says so |
| Save as `.smoke.ts` (branch, `pages/`, `fixtures/`, `tests/smoke/`, `SMOKE` project, `rebalanceShards.mjs`) | Repo code | Only inside kinoa-test-automation. Elsewhere: refused with the reason |
| `page-object-author`, `testops-to-playwright` | Sibling repo skills | Named as kinoa-test-automation skills, used only on the save-as-spec path |

**Deleting the old copies** covers every reference in kinoa-test-automation, not only
`.claude/skills/README.md`: `CLAUDE.md` (lines 29, 303-306), `playwright.config.ts:205`,
`testops-manual-run/SETUP.md` (lines 31, 113), `.claude/skills/docs/README.md:19` and
`qa-skills-guide.html`. KING-22420's paths are updated to point here.

**Packaging.** The `plugin.json` and `marketplace.json` descriptions name the new skills. The
version bump and CHANGELOG entry follow `test_plugin_manifest.py`. The Node scripts come with
whatever tests they have today; adding a Node test harness to this repo is out of scope.

## 3. Rejected options

| Option | Why rejected |
|---|---|
| A third, "focused" format next to smoke and e2e | Every format is a rule set that can drift from the validator. E2E with no length limit already covers short focused cases |
| `smoke` as a case `type` | It writes the same behaviour twice and gives "smoke" a second meaning next to the Story smoke test |
| A selection tag or field for the fast lane | More machinery than needed. The smoke scenario *is* the fast lane |
| A hard 2–5 step gate for smoke | Real scenarios need 6 or 7 steps. A soft target keeps the intent without rejecting valid plans |
| E2E as journeys only, with negative and edge checks folded in as branches | Journeys get long and hard to review, and one failing branch hides the rest of the journey |
| An AC citation on every step in e2e | New grammar with no user. A case-level list of ACs covers it |
| Smoke plans pushed to TestOps by default | Reverses the KING-22213 scope change: a third copy of a plan that runs a handful of times |
| Smoke plans in Jira only, with no TestOps path | Leaves KING-22420 without a starting case |
| `smoke-plan` merged into `testplan` | The outputs differ (Jira sub-task vs TestOps), so one skill would carry two pipelines |
| Leaving the smoke skills in kinoa-test-automation | "Smoke" would stay owned by two repos, which is the conflict this ticket exists to remove |
| Rewriting the Jira scripts in Python | Risk with no gain: they are portable Node already |
| An LLM step that writes the smoke plan from the sub-task | The mapping is mechanical, and a model would drift from the validator. A tested script does not |
| Writing the case id into the sub-task description | The description is the plan (`smoke-run/SKILL.md:129, 298`) |

## 4. Changes this implies (follow-up ticket, per KING-22942 AC-5)

**Validator and parser (`skills/testplan/scripts/`)**

1. `scope:` accepts `smoke | e2e`. `story` FAILs `scope-valid`, naming the allowed set. An
   absent `scope:` means `e2e`: the `or "story"` default (`validate_test_plan.py:148`) and the
   `STORY_SCOPE` default of `target_marker` (`testops_payload.py:63`) both change to e2e.
2. `source: ac:` accepts a comma-separated list of AC ids. `source-valid`, `ac-coverage` and
   `conflict-resolution` check each one. Tested with a real multi-AC value, per CLAUDE.md.
3. Under `scope: smoke`, `ac-coverage` reports uncovered ACs as a warning, not a FAIL. A
   missing `## Acceptance Criteria` section still FAILs.
4. New check `type-valid`: `type` is one of the five values. Today only presence is checked,
   so `type: banana` passes. `type: e2e` FAILs with a message pointing at `scope: e2e`.
5. New check `smoke-shape`: under `scope: smoke`, exactly one case, and it is
   `type: functional`. "Exactly one expected result per step" is already enforced for every
   non-e2e plan (`validate_test_plan.py:108`).

**What the validator enforces** (and so what the reference docs may claim):

| Rule | Enforced by |
|---|---|
| Smoke: one case, `functional` | Validator (`smoke-shape`) |
| Smoke: one `→ expected:` per step | Validator (`required-fields`) |
| Smoke: 2–5 steps | Nobody: guidance in `smoke-plan` only |
| E2E: any type, any length, several expected results per step, several ACs | The validator allows it and nothing requires it |
| Every step has an expected result | Validator (`required-fields`), both formats |

**Allure mapping (§5.1)**

6. `testops_fields.py`: remove `E2E_FEATURE` and the `--feature` error under e2e (lines 13,
   43-52), and update the four tests in `test_testops_fields.py` that assert them. E2E keeps
   status `Review`.
7. `testops-sync.md` (lines 25, 84-94, 464) and the eval assertions in `evals.json` (lines 714,
   744, 755, 790) are rewritten. Eval (d) at line 755 loses its premise, so it is replaced
   rather than edited. Fixtures with no `scope:` line still pass under e2e; what changes is
   their expected outputs.

**`testplan` flow**

8. `--scope` is removed from the generation run: `testplan` generates e2e only. Smoke plans
   reach it only through the push entry point (item 11).
9. The scope carry-forward, the `SCOPE CHANGED` report and the header-disagreement abort
   (`plan_writer.py:46-80`, `SKILL.md:74-81, 101-104, 228-231`) are removed. With one
   generation mode there is nothing to carry forward or disagree with.
10. Plan files stay one per format, `<STORY-KEY>-e2e.test-plan.md` and
    `<STORY-KEY>-smoke.test-plan.md`, so the two reconciliation sets never mix.
11. The push entry point, `/kinoa-qa:testplan --from-smoke <SUBTASK-KEY>`, runs
    `smoke_to_plan.py`, then the validator, the Step D gate and Step E, then the remote-link
    write-back (§2.4).

**References and README (KING-22942 AC-4, shipped with the validator, §5.2)**

12. `test-plan-format.md` and `generation.md` record the taxonomy in §2 and the enforcement
    table above. `generation.md:44` ("six case types") becomes five.
13. "What this plugin does NOT know about e2e authoring" (`generation.md:53-75`,
    `README.md:209-214`) is rewritten. E2E is now the plugin's default output. What stays true
    is that the e2e suite's house style (naming grammar, stepper, publish and WS/InBox blocks)
    is not ported, so the generator must not invent it.
14. The README's scope section and flag table are rewritten.

**Move.** Everything in §2.5, done as one PR here and one deletion PR in kinoa-test-automation.

## 5. Decided at review (2026-09-24)

1. **Which Allure mapping does e2e keep?** KING-22797 set e2e cases to `Feature = "e2e
   scope"` and status `Review`. That was written for journeys. Now that e2e is the
   full-coverage default, every case `testplan` pushes would get that `Feature`, and the
   `Feature` field would stop telling cases apart.
   **Decided:** e2e takes the caller's `Feature` and keeps `Review`. Smoke pushes use the
   caller's `Feature` and `Draft`. The plugin no longer sets the `"e2e scope"` Feature value,
   and passing `--feature` under e2e is no longer an error.
2. **When do the doc updates land?** KING-22942 AC-4 puts the taxonomy into
   `test-plan-format.md` and `generation.md` on this ticket. But CLAUDE.md says a reference
   file that misdescribes the validator is a defect, and until items 1–5 of §4 land, the
   validator still accepts `story` and `type: e2e` and rejects multi-AC sources.
   **Decided:** ship AC-4 in the same PR as the validator changes (the follow-up ticket).
   This ticket closes with the decision comment (AC-1 to AC-3) and the linked follow-up (AC-5).

## 6. Decided after the critic review (2026-09-24)

1. **May `testplan` write to Jira?** The case-id write-back is the plugin's first Jira write.
   It needs the `write:jira-work` scope, which the README says the plugin does not use today.
   **Decided:** yes, limited to adding one remote link on the sub-task, behind the
   Step D confirmation. The alternative is to show the id and ask the user to paste it, which
   is exactly the manual step this push exists to remove.
2. **Where does `step-outcome-contract.md` live?** `testops-manual-run` stays in
   kinoa-test-automation and uses it (`testops-manual-run/SKILL.md:18, 52`), and
   `scripts/packageSkill.mjs` bundles it. Deleting it there breaks that skill.
   **Decided:** the plugin copy becomes the owner. The repo copy stays as a read-only
   mirror, with a header naming the plugin as the source, until `testops-manual-run` moves
   too. The alternative, pointing `testops-manual-run` at a plugin path, ties a repo skill to
   the plugin's install location.
3. **Two items split into their own tickets** (§2.5): the shared source-reading reference,
   and the three improvements from the KING-22213 comment. **Decided:** they are not part of
   the move and get their own tickets.
