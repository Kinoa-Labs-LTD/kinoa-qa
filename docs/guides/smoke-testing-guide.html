kinoa-qa plugin · smoke testing guide

Smoke testing
with Claude

Hand Claude a Story key. Get back a smoke test plan you can read, a real run against TEST, and a straight answer to the only question that matters early: is this feature actually live and testable yet?

The shape of it

Two skills, run in order, both driven by conversation. The Jira sub-task is the single source of truth — the plan lives there, the run report gets posted back there, and anything that looks like a bug is raised against the Story.

Step one — plan it

you say/kinoa-qa:smoke-plan KING-21500
  1. Claude reads the Story, its acceptance criteria, its comments, and any linked Confluence PRD.
  2. It opens the Figma design and reads the real UI copy — labels, states, validation text, empty and error states.
  3. It cross-checks those sources against each other. Where they disagree, that becomes an open question — never a quiet guess.
  4. It shows you a draft and stops. Nothing reaches Jira until you say go.
  5. On your yes: the sub-task is created, and open questions are commented onto the Story for the PO.
What you get Numbered steps, one expected result each, and every result tagged with where it came from — [AC-2], [PRD: section], [Figma: frame]. Steps that prove the feature is live are tagged [GATE].
What to expect
  • It will not invent expected results
  • Untraceable things become questions for the PO
  • Nothing written before you confirm
  • Expect to edit it — it's a strong first draft

Step two — run it

you say/kinoa-qa:smoke-run KING-22281

Claude drives a real browser through the steps on TEST, judging each against its expected result, then posts the report back to the sub-task and hands you an artifact link. Anything that looks like a product defect is raised as a Sub-bug on the Story — with the screenshots attached to it, so the bug arrives complete rather than needing evidence chased later.

On evidence

A screenshot has to show the failure, not the setup for it. If the bug is "the conflict persists after the field is deleted", a picture of the conflict before the deletion shows correct behaviour — it looks like evidence and proves nothing. Files are named after what they show, and attached to whichever ticket they belong to: run evidence on the sub-task, defect evidence on the bug.

Two verdicts — and the difference matters

Feature verdict live / partially live / not live. Is it deployed, reachable, does the main path work — can deeper tests be written now?
Conformance verdict passed / failed / blocked. Does each expected result match what the spec says it should be?
The pairing people misread

live + failed is normal and useful. It means the feature works, but something disagrees with a written spec — which may be a defect, or may be a stale spec. It does not block deeper testing. Only not live stops everything.

Each step gets pass, fail or blocked, with evidence on every non-pass. blocked is not a soft fail: fail says something about the product, blocked says something about the run.

What it found on the first real Story

KING-19550, "Export In-App to a different project" — a Story already marked Completed. The run returned feature: live, and turned up four things a human review had not:

FindingWhy it mattered
Wrong status in the ACThe AC and the PRD both said exported In-Apps are created as Draft. They are created as In-Review. The Story's own notes said so too — the AC contradicted its own Story
A stale PRDThe PRD named a modal and three sections that do not exist in the product. Anyone writing tests from it would have written them wrong
A product bugDeleting a conflicting field in the destination doesn't clear the conflict — it's a soft delete, and the validator still counts it. The operator is left with no way forward. Filed as KING-22355, screenshots attached, and picked up by a developer within days
No test attributesThe export dialog exposes no data-testid, so everything is reached by text — which is why automating it isn't worth it yet

None of these were found by being clever. They were found by insisting every expected result cite a source, then checking those sources against each other and against the running product.

The Jira token trap

Creating the token, you'll be offered granular scopes like write:attachment:jira. They look exactly right and they do not work — Atlassian's gateway rejects every upload with 401 "scope does not match" no matter what you grant. It's a confirmed Atlassian bug, not your setup.

Choose the classic scopes instead: read:jira-work + write:jira-work. Broader than anyone would like — they also permit editing and deleting issues — but it is the only combination that can upload today.

Put the exports in ~/.zshrc, not ~/.zprofile: only login shells read the latter, so tooling won't see your token. Without a token the kinoa-qa plugin's smoke-run stops at the start and names what is missing.

The Figma trap

Being able to open the design in your browser is not enough. The integration also needs you to be a member of the team that owns the file — a direct share or a link gives you browser access without membership, and the tool then refuses with a misleading "you don't have edit access to this file". It is not asking for edit rights.

Ask to be added to the Kinoa Figma team with a Dev seat. A View seat is capped at six API calls a month. Everyone authenticates as themselves — no account is shared. Only smoke-plan needs Figma; smoke-run needs none (both in the kinoa-qa plugin).

What it will not do

Decide what "correct" meansIt surfaces contradictions between the Story, the PRD, the design and the build. A human resolves them.
Replace the regression suiteSmoke means "does the new thing work". Nothing wider.
Write code by defaultThe deliverable is a report. Ask explicitly if you want a committed spec — and prefer promoting to a real regression test instead.
Guarantee the expectations are rightThey are traceable to a source — a weaker claim. On the first Story the most official-looking source was the wrong one. Precedence: live UI > design > PRD.
One safety note

The kinoa-qa plugin's smoke-run works against real data on TEST — it creates and modifies entities. Point it at a sandbox project, not one the CI suite depends on.
