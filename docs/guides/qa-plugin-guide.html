Internal briefing · QA tooling

kinoa-qa

A Claude Code plugin with three skills. testplan turns a Jira Story into a reviewable e2e test plan, and — only after you approve it — into test cases in Allure TestOps. smoke-plan and smoke-run write and run a short Story smoke test on a Jira sub-task. What kinds of case it produces is now agreed — see the decision below.

Three skills, two formats

What each one produces

/kinoa-qa:testplan e2e plan → Allure TestOps

Full coverage of a Story: every acceptance criterion, negative and edge cases, journeys where they fit. A markdown plan you review, then cases in project KINOA.

/kinoa-qa:smoke-plan smoke plan → Jira sub-task

One short scenario, about 2–5 steps, that proves the main feature works. Written as a "Smoke test" sub-task on the Story. It creates no TestOps case itself — testplan --from-smoke pushes the sub-task as one on request.

/kinoa-qa:smoke-run run report → the same sub-task

Drives a real browser through the smoke steps on TEST and posts the report back to the sub-task, with defects raised as Sub-bugs.

Two rules hold for all three: service repositories are read-only — the plugin reads code and specs, never writes them — and nothing is written to Jira or TestOps before you confirm it. The smoke pair has its own QA guide: Smoke testing with Claude.

The testplan run, step by step

Five steps · two places it stops for a human

Aassemble

Gather the source of truth

The Jira Story is the requirement, and it is the one required input. The Confluence PRD, Figma mockups and images attached to the Story refine it — a requirement pasted in as a screenshot is read and tested, not reported as a gap. OpenSpec files from the service repo are context only — a repo with none is the ordinary case, not a degradation.

Bgenerate

Write the plan

Cases are derived from acceptance criteria, the boundaries those criteria imply, and contract changes. The plan header always says scope: e2e. Every case carries a source: line naming the criteria it covers — one or several, like ac: AC-1, AC-3 — so you can always ask "why does this case exist?" and get an answer.

Cvalidate

Check it mechanically

Fourteen checks, no judgement: required fields and sections, valid sources, every acceptance criterion covered, honest gaps, resolved conflicts, valid references (spec, mockup and image), a known scope (smoke or e2e) and a known case type. This is a script — it produces the same verdict every time. testplan only goes on with an e2e plan, unless the run is --from-smoke; otherwise a plan whose header says scope: smoke stops here and is never pushed.

Gate D · the human gate

You read the plan and approve it, or edit and re-run. Nothing has touched Allure TestOps at this point. This gate is not skippable and has no unattended mode.

Eupsert

Push to Allure TestOps

Cases are created or updated in project KINOA, as Review. Re-running a plan updates the same cases instead of duplicating them, because each case remembers the Allure id it was given on first creation.

Gates 0a and 0b · inside step E, before any write

0a re-runs the validator on the plan as it stands — an edit made after approval cannot sneak past. 0b checks each custom-field value is already in use in the project, so a typo stops the run instead of creating cases under a wrong value.

What the validator tells you

Three outcomes · the exit code is the verdict

exit 0 PASS

Structurally sound and every acceptance criterion is covered. Ready for you to read.

exit 1 FAIL

Something is wrong and named — a missing field or section, an uncovered criterion, an unknown scope or type.

exit 2 HOLD

Valid, but a requirement conflict is unresolved. A person decides; the plugin will not pick a winner.

HOLD is the interesting one. When the Story, the PRD and the mockups disagree, the plugin records the conflict and stops rather than quietly choosing whichever source it read last.

Running it

Install · configure · invoke

# install (once)
/plugin marketplace add Kinoa-Labs-LTD/kinoa-qa
/plugin install kinoa-qa@kinoa-qa
# a dry run — writes nothing to Allure TestOps
/kinoa-qa:testplan KING-1234 --dry-run

# a real run
/kinoa-qa:testplan KING-1234 --story-field Template --component Game-Settings --feature In-Apps

# the Story smoke test: plan it, then run it
/kinoa-qa:smoke-plan KING-1234
/kinoa-qa:smoke-run KING-5678

# push that smoke sub-task to TestOps as one Draft case
/kinoa-qa:testplan --from-smoke KING-5678 --story-field Template --component Game-Settings --feature In-Apps

testplan makes e2e plans only

There is no scope flag any more. Every plan testplan writes is an e2e plan at …-e2e.test-plan.md, and a step may carry several expected results, each its own block in TestOps. A smoke plan comes from /kinoa-qa:smoke-plan as a Jira sub-task, not as a test plan file. Passing --scope stops the run and says why.

Pushing a smoke sub-task. --from-smoke <SUBTASK-KEY> generates nothing: a script converts the sub-task, with its parent Story's acceptance criteria, into a smoke plan at …-smoke.test-plan.md, which then goes through the same validator, gate and push as one Draft case. A sub-task the script cannot read — no preconditions, a step without exactly one expected result, no [GATE] step, a Story with no criteria list — is refused with the reason; you fix the sub-task, never the plan file. On a separate yes at the gate, the case id is then recorded on the sub-task as one remote link, Allure TestOps case <id>, which smoke-run reads and a re-push updates in place.

A plan written before version 0.3.0 at …-story.test-plan.md is no longer read. To keep its Allure ids, rename it to …-e2e.test-plan.md and set scope: e2e in its header before the next run.

One caveat: this plugin does not encode our e2e suite's house style — its naming grammar, stepper structure and publish/WS blocks live outside the repo. A generated e2e plan follows the plugin's own rules, and the generator is told not to invent the house style.

Every testplan argument, and whether you must pass it

ArgumentRequired?What it is for
<STORY-KEY>AlwaysThe Jira Story to build the plan from — the one genuinely mandatory input. No Story, no run. Everything else degrades without stopping.
--story-fieldFor step E, unless set in config.jsonThe Allure Story field. Checked before any write: Allure rejects an unknown value silently and fails the whole creation.
--componentFor step E, unless set in config.jsonThe Allure Component field. Same pre-flight check.
--featureFor step E, unless set in config.jsonThe Allure Feature field. Same pre-flight check.
--targetOptionalWhich service capability the plan covers. Decides the plan filename, fills each case's Target: marker (how a re-run finds its own cases) and points the OpenSpec resolver at a spec.
--repoOptionalOverrides which GitHub repo the OpenSpec spec is read from.
--openspec-pathOptionalReads the spec from a local checkout instead of GitHub — useful before it is pushed.
--allow-unverified-fieldsOptionalDowngrades one pre-flight check to a warning. It can prove a field value is in use, never that it exists, so a freshly created value would otherwise abort the run.
--dry-runOptionalWrites nothing and never refuses. A–D run in full; E does read-only lookups and prints what it would create or update.

The three field flags are required because config.json ships its defaults empty on purpose — no run inherits another team's values by accident. Fill them into the config and the flags become optional overrides. This is the most common reason a first run stops.

JIRA_EMAIL and JIRA_API_TOKEN are read by two skills, differently. testplan uses them to read images attached to the Story; without them it continues and records images: none (jira credentials not set). Under --from-smoke it also writes the sub-task's remote link with them, which needs the classic write:jira-work scope; without them the case is still pushed and you add the link by hand. smoke-run needs them to post its report, so without them it stops at the start and names what is missing.

What we decided

KING-22942 · agreed 24 September

Most of our cases used to be written as one long journey. Before generating cases in bulk, we agreed what kinds of case the plugin produces — because it will faithfully produce whatever we tell it to, several hundred times. Three things had been tangled into one word; each now has one meaning.

Format — how a case is written

Exactly two, set by the plan's scope: line. Smoke is one short functional scenario — about 2–5 steps, as guidance, not a limit — on a Jira sub-task. E2E is the full coverage of a Story: any case length, several expected results per step, several criteria per case. There is no third format.

Type — what a case is for

functional · negative · edge · regression · nonfunctional. e2e left the list: it is a format, and the format lives in the plan header. The validator now rejects any other type.

Selection — when a case runs

Not a separate axis. The smoke scenario is the fast lane — no smoke tag, no selection field. "Smoke" means only the Story smoke test, and the plugin now owns both smoke skills.

questionIs the main feature live and working?Is the Story fully covered?

A finished smoke sub-task goes into TestOps only on request, with /kinoa-qa:testplan --from-smoke (0.5.0, KING-23102); without that, a smoke test lives only in Jira.

Honest status

Read this before you trust it · checked 28 September

  • The deterministic core is well tested. Parser, validator, payload builder, field resolver, the id merge, the attachment reader, the smoke converter smoke_to_plan.py, the link writer jira_remote_link.py and the two smoke-run Jira scripts are covered by 472 tests, run in CI on every pull request.
  • Steps A–D have run for real once, on KING-18454 — 15 cases across 15 acceptance criteria, validator-clean. That plan predates version 0.3.0, so it sits at the old …-story path: rename it and set scope: e2e before pushing. Step E has still never run: project KINOA holds zero plugin-authored cases, so the upsert, the reconciliation gate and the id write-back remain untested against the real server.
  • Two stops rest on prose, not code. Refusing a passed --scope, and stopping at Step C on a scope: smoke plan outside --from-smoke, live in the skill's instructions with no script enforcing them.
  • The smoke skills are moved, not changed. They came over from kinoa-test-automation in 0.4.0 with only the edits the move needed. Nothing uploads a TestOps launch for a smoke run yet; smoke-run says so. Some bugs already in the moved Jira scripts are waiting for a follow-up ticket.
  • The sensible next step is still the first real push. Take the KING-18454 plan through step E with the three custom-field values, and look at those cases in TestOps before anyone generates in volume.
